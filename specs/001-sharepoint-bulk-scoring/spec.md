# Feature Specification: Bulk Background Scoring from SharePoint and OneDrive

**Feature Branch**: `001-sharepoint-bulk-scoring`  
**Created**: 2026-10-02  
**Status**: Draft  
**Contract Revision**: OpenAPI 3.1.0 planned target; requirement-to-operation mapping is frozen in
`contracts/openapi.yaml` and does not claim runtime activation before the sequenced gates.  
**Input**: User description: "Allow recruiters to upload bulk files from a SharePoint folder for scoring in a background job that continues after the recruiter closes their browser or shuts down their machine." Revised: the source may also be a work or school OneDrive folder, authorized dynamically by each recruiter through a Microsoft 365 source connection that is separate from product sign-in.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Start Scoring from SharePoint or OneDrive (Priority: P1)

As a recruiter working on a job, I can select a SharePoint or OneDrive folder containing candidate documents and submit its eligible files for scoring so that I do not need to download and upload the documents manually.

**Why this priority**: Selecting a shared folder and successfully starting a durable scoring request is the feature's primary value.

**Independent Test**: While signed in to the product, paste an accessible work or school SharePoint folder URL and, separately, an accessible work or school OneDrive folder URL from any organizational tenant in Microsoft commercial cloud. Complete the Microsoft 365 source connection as a user who can access each exact folder, review supported and unsupported files, and submit the eligible files. In each case the folder is verified with that user's delegated access, the request is accepted, eligible files are scheduled for scoring against the selected job, and unsupported files are reported without blocking the eligible files.

**Acceptance Scenarios**:

1. **Given** a recruiter can access a job, **When** the recruiter pastes any valid work or school SharePoint or OneDrive folder URL, **Then** the system starts a separate Microsoft 365 source connection, returns the recruiter to the same job after authorization, verifies access to that exact folder as the connected user, and only then shows discovered files and exclusion counts.
2. **Given** the folder contains supported candidate documents, **When** the recruiter confirms the import, **Then** the system creates one durable bulk scoring request associated with the job and records each selected document as an item in that request.
3. **Given** the folder contains unsupported, inaccessible, or oversized files, **When** the folder is reviewed, **Then** excluded files are summarized as counts by reason without being listed individually, items that could not be read are reported as a count without names, and eligible files remain available for submission.
4. **Given** duplicate documents are found, **When** the request is submitted, **Then** the existing duplicate-handling rules for the job are applied, each skipped duplicate is reported, and the recruiter can choose the existing "allow duplicates" option (off by default) exactly as in the other upload paths.
5. **Given** the connected Microsoft 365 user does not have permission to access the selected folder or its contents, **When** exact-folder access is checked, **Then** discovery and submission are prevented and the recruiter receives a clear permission-related message without exposing restricted content.
6. **Given** the recruiter is reviewing a folder before submission, **When** the submission options are displayed, **Then** an option to convert files to image-based (raster) PDFs before scoring is available and is off by default.
7. **Given** the recruiter enables the raster PDF option and confirms the import, **When** each eligible file is processed, **Then** the file is converted to an image-based PDF in which each page is a rendered image of the original page, and the converted version is the document that is scored. Plain-text (TXT) files are the exception: they bypass conversion and are scored in their original form.
8. **Given** the recruiter leaves the raster PDF option off, **When** the request is processed, **Then** files are scored in their original form exactly as they are today.
9. **Given** the folder holds more files than one discovery step covers (1,000 eligible files), **When** a step completes, **Then** the system states clearly which files are included and that everything else, including entries not yet scanned, is excluded, and asks whether to discover more; only files found before confirmation are imported.
10. **Given** discovery reaches the frozen file-count or bulk total-bytes limit for a request, **When** the limit is hit, **Then** discovery stops before exceeding it, the recruiter is told which limit was reached and that remaining files are not included, and the recruiter may still confirm the files found.
11. **Given** the recruiter pastes a link to a OneDrive folder, **When** discovery starts, **Then** the system recognizes it as a OneDrive source, and the recruiter goes through the same steps as for SharePoint, with the folder listed under its OneDrive owner's name.
12. **Given** a request from any supported organizational tenant has been accepted, **When** processing continues after the recruiter has left, **Then** the product reads only the confirmed folder and its discovered items with delegated read permission as the Microsoft 365 user who confirmed the request, and never substitutes application-only or another user's access.
13. **Given** the request-specific source authorization lapses, is revoked, or loses access to the folder while the request is running (for example the organization's sign-in policy ends the session, the password is reset, the source account is disabled, or the folder permission is removed), **When** the lapse is detected, **Then** every further source read stops immediately, only items that still need source access fail with a clear reconnect-and-retry reason, securely imported items and items already converting or scoring continue to completion, completed items are unaffected, the recruiter is notified, and no fallback identity is used.
14. **Given** a request reaches a finished state (completed or cancelled), or confirmation is abandoned after source authorization was obtained, **When** processing ends, **Then** the system discards the corresponding source authorization and records its lifecycle event without recording or exposing the secret itself.
15. **Given** the recruiter pastes a link that is not to a work or school SharePoint or OneDrive location (for example a personal Microsoft account OneDrive), **When** connection or discovery starts, **Then** nothing is read and the recruiter is told that only work or school SharePoint and OneDrive are supported.
16. **Given** product sign-in is current but no source connection exists for the pasted folder, **When** the recruiter starts discovery, **Then** the product requires Microsoft 365 source authorization and does not treat product sign-in as permission to read the source.
17. **Given** the source tenant permits user consent, **When** the recruiter authorizes the requested delegated read access, **Then** the recruiter can return and continue exact-folder verification without administrator involvement.
18. **Given** the source tenant requires administrator consent, **When** the recruiter attempts to connect, **Then** no folder content is read and the product presents a clear admin-consent-required action and a way to resume after consent is granted.
19. **Given** discovery has included draft items, **When** the recruiter reviews the draft before confirmation, **Then** every included item is available through a server-paginated review list with a stable total and ordering, and moving through review pages does not discover or include additional items.
20. **Given** more source entries remain undiscovered, **When** the recruiter chooses to continue discovery, **Then** discovery continuation is a separate explicit action from moving through review pages, and the review total changes only after a discovery step completes.
21. **Given** a recruiter confirms a request under scoring configuration version A and the job later changes to version B before or during processing, **When** items are scored and the request is reviewed, **Then** the request retains A as the version captured at confirmation, each item uses the job's current configuration when that item is scored, and the request shows that results may use a version different from A.
22. **Given** a source belongs to a Microsoft national, sovereign, government, or other non-commercial cloud, **When** the recruiter starts a connection, **Then** the connection is rejected before authorization or source access and the recruiter is told that this release supports Microsoft commercial cloud only.
23. **Given** a connection-start or callback request exceeds a pending-connection or rate limit, **When** the request is rejected, **Then** the product returns a safe rate-limit response without redeeming an authorization code, acquiring a token, or making a source call.

### User Story 2 - Continue Scoring Without the Recruiter's Device (Priority: P2)

As a recruiter, I can close my browser or shut down my machine after the bulk request is accepted and have importing and scoring continue so that long-running work does not depend on my device remaining available.

**Why this priority**: Device-independent continuation is the key operational improvement over a browser-bound upload.

**Independent Test**: Submit a folder with enough documents to remain active, wait for acceptance confirmation, close the browser and shut down the submitting machine, then return from another device. Processing continues during the absence and the same request shows its current durable state.

**Acceptance Scenarios**:

1. **Given** a bulk scoring request has been accepted, **When** the recruiter closes the browser, loses connectivity, or shuts down the submitting machine, **Then** all pending import and scoring work continues without relying on that browser or machine.
2. **Given** the recruiter leaves while processing is active, **When** the recruiter later returns on any authorized device, **Then** the recruiter can view the latest request status and all completed item outcomes.
3. **Given** the recruiter closes the browser before the system confirms acceptance, **When** the recruiter later returns, **Then** the system does not imply that the request was accepted and the recruiter can safely submit it again.
4. **Given** some documents fail to import or score, **When** other documents remain processable, **Then** unaffected documents continue and the request reports partial success rather than failing as a whole.
5. **Given** a transient interruption affects background processing, **When** processing resumes or retries, **Then** a document is not imported, converted, or scored more than once for the same request item.
6. **Given** the raster PDF option was enabled, **When** the recruiter's device is closed or shut down after acceptance, **Then** conversion and scoring of all remaining items continue in the background without the recruiter's device.
7. **Given** a request has been accepted, **When** the recruiter closes the browser or shuts down the device, **Then** the background work continues using the confirming user's request-specific Microsoft 365 source authorization, not anything on the device, and it does not need the recruiter to reconnect unless the source tenant's policies end that authorization (see User Story 1, scenario 13).

### User Story 3 - Monitor and Recover Bulk Work (Priority: P3)

As a recruiter, I can monitor aggregate and per-file progress, cancel remaining work, and retry failed items so that I can manage large submissions without repeating successful work.

**Why this priority**: Visibility and recovery make unattended processing trustworthy and reduce manual rework.

**Independent Test**: Run a request containing successful, duplicate, failed, and still-processing documents. Verify aggregate counts match item states, cancel outstanding work, and create a retry containing only failed items.

**Acceptance Scenarios**:

1. **Given** a request is active or complete, **When** the recruiter views its details, **Then** the recruiter sees the source folder, associated job, submitter, submission time, current state, and whether raster PDF conversion was requested, and counts for discovered, excluded, waiting, importing, converting, scoring, completed, failed, skipped, and cancelled items.
2. **Given** an item is not successful, **When** the recruiter views its details, **Then** the recruiter sees the file name, current state, and an actionable reason when available.
3. **Given** a request has waiting or active items, **When** the recruiter cancels it, **Then** no new items start, active import and conversion work is asked to stop where possible, completed outcomes remain unchanged, and all remaining items eventually reach a terminal state. Files already handed to scoring continue to completion; the request shows how many are still finishing and ends as cancelled once they have settled.
4. **Given** a completed request contains failed or cancelled items, **When** the recruiter chooses to retry, **Then** a new request contains only the items that failed or were cancelled before being handed to scoring and are retryable, plus any unfinished items failed by a source-authorization lapse, and the original request remains unchanged. Failures caused by scoring itself are handled through the existing job-level controls.
5. **Given** all request items have reached a terminal state, **When** the request status is finalized, **Then** it indicates whether all eligible items succeeded, some items failed or were skipped, no items succeeded, or the request was cancelled.
6. **Given** an authorized recruiter monitors a current or historical request, **When** request summary or detail data is returned, **Then** it includes a safe `authorizationState`; requests for which the state was not recorded show `unavailableHistorical` rather than guessing.

### Edge Cases

- The selected folder is empty or contains no supported candidate documents; once the whole folder has been scanned and nothing eligible was found, no request or draft is created and the recruiter is told why. If a scan step finds nothing eligible but entries remain unscanned, the recruiter is told and can choose to discover more.
- The selected folder contains nested folders; all supported files in the selected folder and its descendants are included in discovery, and inaccessible descendants are reported as a count of unreadable items without exposing their names or contents.
- A folder holds very many entries that are not candidate documents; a discovery step stops after a bounded amount of scanning even if it found few eligible files, reports how far it got, and lets the recruiter continue.
- A file is added, changed, moved, or deleted after discovery; the submitted request uses the files identified during discovery up to confirmation and reports any item that is no longer retrievable or has changed before import.
- Two recruiters submit the same folder to the same job; existing duplicate-handling rules prevent unintended duplicate applications while both requests retain accurate item outcomes. Each request uses only its own recruiter's authorization.
- The request-specific source authorization lapses or access to the source ends while the request is running (the source tenant's sign-in policy ends the session, the password is reset, the source account is disabled, the connected user leaves the organization, the folder permission is removed, consent is revoked, or the request runs longer than the policies allow); all further source reads stop immediately, only items still needing source access fail with an access-related reason asking the recruiter to reconnect and retry, and securely imported, converting, or scoring items finish without source access. The request does not fail as a whole, the recruiter is notified, and the product never switches to application-only access or another identity.
- A link points to a personal Microsoft account OneDrive or any location that is not a work or school SharePoint or OneDrive; it is rejected before anything is read, with a message that only work or school locations are supported.
- A valid work or school folder URL is in a tenant that differs from the product account's tenant; the same connection, verification, preview, and confirmation journey applies without a cross-tenant mode or different source UI.
- The source tenant blocks user consent or requires administrator approval; the recruiter sees an admin-consent-required action, no source names or content are returned, and the flow can be resumed after approval.
- The product user connects a different work or school Microsoft 365 identity; job permissions continue to be evaluated using product sign-in, while source access is evaluated only as the connected Microsoft 365 identity and is bound to that product user, job, and exact folder.
- A source connection is created but the recruiter leaves before confirmation; its short-lived authorization is discarded when it expires or the flow is abandoned and cannot be reused for another product user, job, or folder.
- A retry is started; it requires the retrying recruiter to reconnect a work or school Microsoft 365 identity with current access to the exact folder, so another recruiter retrying a request needs their own source connection and access.
- File names are identical in different subfolders; each item retains enough source context to distinguish it without relying on file name alone.
- Discovery reaches the frozen maximum number of files or bulk total bytes for a request; discovery stops before exceeding either value, the recruiter is told which limit was reached and that remaining files are not included, and the recruiter may confirm the files found. Nothing beyond either limit is imported.
- Scoring configuration changes after confirmation; the request retains the version captured atomically at confirmation, each file is scored with the job's current configuration when that item reaches scoring, and the request shows a changed-version notice whenever the current or used version differs from the captured version.
- A recruiter pages through a large draft review; every included item remains reviewable in a stable server-paginated list, and changing review pages neither advances source discovery nor changes the set of included items.
- Historical requests predate authorization-state tracking; monitoring reports `unavailableHistorical` and does not infer that authorization is active.
- The same request is resumed after an interruption; completed items are not imported, converted, or scored again.
- A file cannot be converted because it is corrupt, password-protected, or otherwise unrenderable; that item fails with a conversion-related reason, is not silently scored in its original form, and does not affect other items.
- A file is already a PDF, including one that is already image-based; when the option is enabled it is still converted to a consistent image-based PDF, so every scored document in the request (other than plain text) is treated uniformly.
- A plain-text (TXT) file is selected while the option is enabled; it bypasses conversion, is scored in its original form, and the item records that the original version was scored.
- A converted file exceeds the permitted document size limit; the item fails with a size-related reason rather than being scored in its original form.
- A multi-page document is converted; every page is preserved in original order, and a document with pages that cannot be rendered fails as a whole rather than being scored with missing pages.
- A retry request is created from a request that used raster conversion; the retry uses the same conversion choice as the original request.
- A recruiter cancels a request and later wants to continue; items cancelled before import can be retried in a new request without scanning the folder again, subject to the same access check as a new request.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST allow an authorized recruiter to paste any valid work or school SharePoint or OneDrive folder URL and start a bulk scoring request for a job they are permitted to manage. The source kind and stable identity of the exact folder MUST be recognized from the URL and recorded on the request.
- **FR-002**: Product sign-in and Microsoft 365 source authorization MUST remain separate. Pasting a supported folder URL MUST start an interactive multi-tenant authorization-code source connection when no valid connection exists for that product user, job, and exact folder; successful source authorization MUST return the recruiter to the pending folder journey without changing their product identity or job permissions.
- **FR-002A**: The source connection MUST request delegated, read-only access and MUST read as the connected work or school user. It MUST support source users from any organizational tenant in the Microsoft commercial cloud that permits the connection. Personal Microsoft accounts and Microsoft national, sovereign, government, or other non-commercial clouds MUST NOT be accepted in this release.
- **FR-002B**: Before returning any folder or file name, content, or preview count, the system MUST use the connected user's delegated access through Microsoft Graph to verify that the URL resolves to a folder and that the connected user can access that exact folder. A failed check MUST reveal no restricted source details.
- **FR-002C**: Discovery and preview MUST be limited to the verified folder and its descendants. The system MUST NOT use the connection to browse, search, preview, or process any other location, even if the connected user can access it.
- **FR-002D**: Before confirmation, the source connection and its authorization data MUST be encrypted and bound to exactly one product user, job, and verified folder. It MUST NOT be usable for another user, job, folder, or purpose. Unconfirmed authorization MUST expire after 30 minutes without recruiter activity and no later than 2 hours after it was obtained, and MUST be discarded on expiry or abandonment.
- **FR-002E**: On confirmation, the system MUST create or bind encrypted source authorization specifically for the accepted request before reporting acceptance. Background workers MUST be able to use only that request-specific authorization for the confirmed folder and items; a pre-confirmation source connection MUST NOT become a reusable general connection.
- **FR-002F**: All source reads, including background reads after the recruiter leaves, MUST use delegated access as the connected user who confirmed the request. The system MUST NOT use application-only access, deployment-time host or root allowlists, pre-granted site or drive access, another user's authorization, or any fallback identity.
- **FR-002G**: Cached source authorization secrets, including authorization codes, access or renewal credentials, token material, protected cache material, and raw source account identifiers, MUST never be returned to a browser or other client after the connection flow completes, exposed to users or administrators, or written to logs, traces, metrics, audit payloads, errors, or redirects. Audit records MAY contain only non-secret lifecycle facts, the product actor, opaque request or connection references, safe state, and timestamps needed to show when authorization was obtained, bound, expired, or discarded.
- **FR-002G1**: Folder names, item names, and the verified source web URL MAY appear only in authorized draft/request DTOs and their authorized recruiter UI surfaces after the caller is authorized for the associated job; the raw submitted folder URL MUST NOT be retained or disclosed outside the protected pending connection. An authorized draft/request DTO or UI MAY label the source account with its display name or a masked email address. Logs, traces, metrics, audit payloads, errors, redirects, unauthorized responses, and administrator-generic surfaces MUST NOT contain folder or item names, any raw or verified folder URL, raw source account identifiers, token material, or an unmasked source email. In place of those prohibited values, those surfaces MAY contain only the opaque connection ID, safe connection or authorization state, and an applicable stable public error code.
- **FR-002H**: The system MUST discard request-specific source authorization when the request reaches a terminal state, is cancelled and all in-progress source reads have settled, or the authorization can no longer be used. It MUST discard unconfirmed source authorization when confirmation is abandoned or its short lifetime ends.
- **FR-002I**: When request-specific authorization lapses or is revoked, or the connected user loses source access, the system MUST immediately stop every further source read. It MUST fail only non-terminal items that still require source access, with a clear reason that tells the recruiter to reconnect and retry. Items whose source content was already securely imported, including items queued for conversion or scoring and items already converting or scoring, MUST continue to a terminal outcome without further source access. Completed outcomes MUST remain unchanged, the recruiter MUST be notified, and the system MUST NOT use application-only access, another user, cached content from another request, or any other fallback.
- **FR-002J**: The source connection MUST allow user consent where the source tenant's policy permits it. If administrator consent is required, the system MUST read no source content, MUST present a clear admin-consent-required action, and MUST allow the recruiter to resume the pending connection after consent is granted.
- **FR-002K**: The folder journey and capabilities MUST be the same regardless of whether the source tenant matches the product user's tenant. The system MUST NOT expose a same-tenant/cross-tenant mode or require deployment-time folder authorization.
- **FR-002L**: The system MUST reject, before reading anything, a URL that is not a work or school SharePoint or OneDrive folder (including a personal Microsoft account OneDrive), and MUST tell the recruiter that only work or school SharePoint and OneDrive folders are supported.
- **FR-002M**: The system MUST allow at most 10 pending source connections per authenticated product actor. Connection starts MUST be limited to 10 per rolling minute per actor and 30 per rolling minute per source IP address; authorization callbacks MUST be limited to 60 per rolling minute per source IP address. A request rejected by any of these controls MUST receive a safe `429` response and MUST cause no authorization-code redemption, token acquisition or refresh, Microsoft Graph call, or other source read.
- **FR-002N**: Publisher-verification gating MUST be based only on the product deployment environment and the Microsoft 365 connector registration status, never on the selected source tenant. In Production, application startup or feature activation MUST require an explicit configuration assertion that the connector has verified-publisher status and MUST fail closed when that assertion is absent or false. Before verification, the connector MAY operate only in controlled non-production Development or QA deployments whose product-user access is already restricted by normal application authorization. The system MUST NOT inspect, classify, or allow-list any source tenant for rollout gating.
- **FR-003**: The system MUST discover supported candidate documents in the selected folder and its descendant folders.
- **FR-003A**: Discovery MUST proceed in steps of up to 1,000 eligible files. After each step the system MUST report what has been included, MUST state that everything else (including entries not yet scanned) is excluded, and MUST let the recruiter choose to discover more or to confirm what has been found. A step MUST stop after a bounded amount of scanning even if it found fewer eligible files, and MUST report how far it got. Continuing discovery MUST be an explicit action independent from review-list pagination.
- **FR-004**: Before submission, the system MUST show the number of files that will be imported and their total size, MUST summarize everything else as counts of excluded entries by reason (without listing excluded entries individually), and MUST show the count (without names) of items that could not be read. Every included draft item MUST be independently reviewable through a server-paginated list with a stable total and deterministic ordering up to the frozen request limits. Navigating review pages MUST NOT continue discovery, change discovery continuation, or add items.
- **FR-005**: The system MUST enforce the supported document types, the individual file-size limit configured in System Configuration > Settings (the same per-file maximum used by the optional parallel upload, 8 MiB by default when no value has been saved), the maximum number of files per request (FR-005B), and the environment-owned bulk total-bytes limit (FR-005C). When discovery reaches the frozen file-count or total-bytes limit it MUST stop before exceeding it and tell the recruiter which limit was reached and that remaining files are not included.
- **FR-005A**: In both technology stacks, the System Configuration > Settings screen MUST present the per-file and in-flight upload limits in MiB (1 MiB = 1,048,576 bytes) instead of raw bytes without changing any saved byte values. Only installations with no saved per-file value use the new 8 MiB per-file default (previously 4 MiB); the unchanged in-flight default is 100 MiB.
- **FR-005B**: An authorized system administrator MUST be able to set, in System Configuration > Settings, the maximum number of files per bulk scoring request. The default MUST be 30,000 and accepted values MUST be whole numbers from 1 through 100,000 inclusive. A draft MUST capture and freeze the value in effect when discovery starts; changes apply only to later drafts. Changes MUST be validated, versioned, and recorded in the audit trail.
- **FR-005C**: The bulk total-bytes limit MUST be owned by environment configuration rather than the administrator UI, MUST default to 50 GiB (53,687,091,200 bytes), and MUST accept values from 1 MiB (1,048,576 bytes) through 1 TiB (1,099,511,627,776 bytes) inclusive. A draft MUST capture and freeze the value when discovery starts; environment changes apply only to later drafts.
- **FR-006**: The recruiter MUST be able to confirm or abandon the discovered selection before a request is accepted.
- **FR-007**: Upon confirmation, the system MUST durably record the bulk request and its individual source items before reporting that the request was accepted.
- **FR-008**: Each accepted request MUST be associated with exactly one job, one submitting user, and one source folder.
- **FR-008A**: In the same confirmation outcome that durably creates the request, the system MUST capture the job's scoring configuration version current at confirmation. Each item MUST be scored with the job's current configuration when that item reaches scoring, not forcibly with the captured version. The request detail and monitoring data MUST retain the captured version and MUST show a changed-version notice whenever the job's current version or an item's used version differs from the captured version.
- **FR-009**: Importing and scoring for an accepted request MUST continue independently of the submitting browser, network connection, or device.
- **FR-010**: The system MUST preserve the established document validation, duplicate-handling, candidate extraction, scoring, aggregation, and human-review behavior for documents imported from SharePoint or OneDrive, except for the standardized content fingerprint defined in FR-010H.
- **FR-010A**: The system MUST offer the recruiter, per request and before confirmation, an option to convert each file to an image-based (raster) PDF before scoring. The option MUST be off by default.
- **FR-010B**: When the option is enabled, the system MUST convert every eligible item in the request to an image-based PDF before scoring it and MUST score the converted document instead of the original. The converted document MUST preserve the source page count and page order; each output page MUST retain its corresponding source page dimensions within ±1 point; and, when the source and output pages are rendered at the configured DPI, each output page MUST achieve SSIM >= 0.95 against its corresponding source page and MUST be neither blank nor cropped. Plain-text (TXT) files are exempt: they bypass conversion and are scored in their original form.
- **FR-010C**: The system MUST retain the original source file for each converted item alongside its converted version, MUST identify which version was scored, MUST present the scored (converted) version by default wherever the document is viewed, and MUST let reviewers download the original.
- **FR-010D**: If conversion of an item fails, the system MUST mark that item failed with a conversion-related reason and MUST NOT silently fall back to scoring the original file.
- **FR-010E**: The system MUST record the conversion choice with the request when it is accepted, and the choice MUST NOT change for that request afterward. A retry request MUST inherit the original conversion choice.
- **FR-010F**: Raster PDF conversion MUST run as part of the background work and MUST continue without the recruiter's browser or device, with the converting state visible in progress and per-item status.
- **FR-010G**: Converted documents MUST meet the same size limits and validation rules as other documents before scoring, and the system MUST report any item that fails them.
- **FR-010H**: The system MUST detect duplicates with one consistent content fingerprint, the SHA-256 of the file's raw bytes, across the bulk scoring request, the optional parallel upload, and the existing upload in both technology stacks, so the same file is recognized as a duplicate whichever path introduced it. Documents uploaded before this change MUST still be recognized as duplicates.
- **FR-010I**: The system MUST retain the existing "allow duplicates" option, off by default, and MUST offer it when starting a bulk scoring request so that duplicate handling can be demonstrated and tested.
- **FR-011**: Failure, exclusion, duplication, or cancellation of one item MUST NOT prevent other eligible items from continuing.
- **FR-012**: The system MUST prevent a retry or resumed operation from creating duplicate imports, duplicate converted documents, or duplicate scores for the same request item.
- **FR-013**: The system MUST expose durable aggregate progress and per-item status to authorized recruiters after they leave and return from any device.
- **FR-013A**: Every authorized request-summary and request-detail monitoring DTO MUST include `authorizationState` with one of the stable public values `pending`, `active`, `lapsed`, `revoked`, `accessLost`, `discarded`, or `unavailableHistorical`. `unavailableHistorical` MUST be used when a trustworthy state is unavailable, including historical records created before the field existed; the system MUST NOT infer an active state.
- **FR-014**: Every processed item MUST transition to a terminal outcome of completed, failed, skipped, or cancelled, and the parent request MUST remain active until all such items are terminal. Entries excluded during discovery are never processed and are shown only as counts by reason.
- **FR-015**: The system MUST provide a clear, actionable reason for failed, skipped, and cancelled items, and a reason category for excluded entries, whenever such a reason is available.
- **FR-015A**: Public authorization and connection failures MUST use one of these stable error codes: `source_authorization_required`, `source_admin_consent_required`, `source_authorization_expired`, `source_authorization_revoked`, `source_access_denied`, `source_connection_invalid_or_expired`, `source_connection_limit_reached`, `source_connection_rate_limited`, `source_callback_rate_limited`, `source_unsupported_account`, `source_unsupported_cloud`, or `source_folder_invalid_or_unavailable`. Public messages and status codes MUST remain safe under FR-002G1 and MUST NOT distinguish hidden folder existence, account identifiers, token details, or other restricted source facts.
- **FR-016**: An authorized recruiter MUST be able to cancel an active request without altering already completed outcomes; files already handed to scoring MUST continue to completion and the request MUST show how many are still finishing.
- **FR-017**: An authorized recruiter MUST be able to create a new retry request containing only items that failed or were cancelled before being handed to scoring and are retryable (such as a temporary source or conversion problem, a source file that changed after discovery, or an item cancelled before import), plus any unfinished items failed under FR-002I by a source-authorization lapse. Failures caused by scoring itself are not retried by this feature and remain with the existing job-level controls.
- **FR-017A**: Before creating a retry request the system MUST require a new Microsoft 365 source connection from the retrying recruiter, verify delegated access to the exact source folder under FR-002B, refuse the retry with a clear permission-related message if the check fails, and create fresh request-specific authorization under FR-002D through FR-002I. Authorization retained from the original request MUST NOT be reused.
- **FR-018**: The original request and its item outcomes MUST remain unchanged when failed items are retried.
- **FR-019**: The system MUST record the submit actor and submission time for every accepted request and, when cancellation is requested, the cancel actor and cancellation time. These fields MUST be exposed only on request detail that the viewer is authorized to access under FR-022. For each actor, the system MUST resolve the display name from the corresponding user record and MUST fall back to the recorded actor identifier when that user record or display name is unavailable; both the normal display-name path and the actor-identifier fallback path MUST be supported.
- **FR-020**: On every request's first transition to a terminal state, the system MUST create an in-product notification for only the recruiter who submitted that request. The notification MUST include the terminal outcome; aggregate completed, failed, skipped, and cancelled item counts; and a link whose target enforces authorized access to the request detail. Its payload MUST NOT contain item names. The submitting recruiter MUST be able to acknowledge the notification once; acknowledgment MUST be retained, and repeated acknowledgment attempts MUST NOT create another acknowledgment or notification.
- **FR-021**: The system MUST delete a bulk scoring request, its items, and any retained original or staged files when the associated job is deleted, MUST keep the audit trail entries for the request's state changes, and MUST otherwise retain request status and item outcomes for as long as the job exists.
- **FR-022**: The system MUST prevent users without access to the associated job from viewing, cancelling, retrying, or otherwise managing the request.

### Key Entities

- **Bulk Scoring Request**: A durable submission of candidate documents from one SharePoint or OneDrive folder to one job; includes submitter, source kind, source folder identity, recorded scoring context, raster PDF conversion choice, discovery progress, excluded-entry counts by reason, timestamps, aggregate status, counts, and terminal outcome.
- **Bulk Scoring Item**: One included source document within a request; includes source identity and path, observed document details, processing state, outcome reason, the original and any converted version, which version was scored, and relationship to any resulting application and score. Excluded entries are not items.
- **Discovery Step**: One pass over the source folder that finds up to 1,000 eligible files, tallies excluded and unreadable entries, and records where to resume.
- **Bulk Scoring Setting**: The administrator-configured maximum number of files per request (default 30,000; accepted range 1 through 100,000) and the environment-owned bulk total-bytes limit (default 50 GiB; accepted range 1 MiB through 1 TiB), with both values captured and frozen when discovery starts.
- **Converted Document**: The image-based PDF produced from an item's original file when conversion is requested; includes its relationship to the original, page count, size, and conversion outcome.
- **Source Folder**: The selected SharePoint or OneDrive folder, its source kind, and its owner (for OneDrive), together with enough information to identify its contents without exposing restricted locations.
- **Pending Source Connection**: A short-lived, encrypted delegated connection established by a product user with a work or school Microsoft 365 identity; bound to one product user, job, and verified folder until confirmation or abandonment. It has an opaque connection ID and safe authorization state; its authorization data and raw source identifiers are never visible to users or administrators.
- **Request Source Authorization**: The delegated permission held for exactly one accepted request to read the confirmed folder as the connected user; includes only non-secret lifecycle metadata about who connected, its bindings, state, and when it was obtained and discarded. The authorization data itself is never returned or logged.
- **Scoring Context**: The job and the scoring configuration version recorded when the request is accepted, so reviewers can see whether the configuration changed afterwards.
- **Processing Event**: An auditable request- or item-level transition such as acceptance, import, conversion, scoring, failure, retry, cancellation, or completion, including actor or system origin and time.

## Assumptions

- Recruiters already have authenticated product accounts and job-level permissions; this feature does not introduce a new recruiter role.
- Product authentication establishes the recruiter's product identity and job permissions but grants no SharePoint or OneDrive access. Each folder journey uses a separate Microsoft 365 source connection, which may use a different work or school identity and may belong to any organizational tenant in Microsoft commercial cloud that permits the connection.
- For both SharePoint and OneDrive, the product reads the exact confirmed folder on behalf of the connected user and under that user's current permissions. The product has no standing, deployment-time, or application-only access of its own to SharePoint or OneDrive content.
- Only work or school OneDrive accounts are supported. Personal Microsoft account OneDrive is out of scope.
- A recruiter may paste any valid work or school SharePoint or OneDrive folder URL that the connected source identity can open, including folders colleagues have shared with that identity; no permission to share or administer the folder is needed.
- Source tenants may allow users to consent directly or may require an administrator to approve the delegated connection. Tenant policy remains authoritative; the product guides the recruiter to the applicable action and does not bypass it.
- Because background work runs on request-specific delegated authorization, it is subject to the source tenant's sign-in, consent, and session policies. A request that runs longer than those policies allow, whose authorization is revoked, or whose connected user loses access immediately stops all further source reads and fails only items that still require source access under FR-002I; securely imported, converting, and scoring items finish without the source connection. Retry requires a new connection.
- Source authorization is retained only as encrypted authorization data; no unencrypted credential or token is retained, returned, or logged. Before confirmation it expires after 30 minutes of inactivity and no later than 2 hours after it was obtained, and is bound to the product user, job, and folder; after confirmation it is additionally bound to the accepted request.
- Existing supported document types, scoring behavior, retention rules, and human-review safeguards remain authoritative. The individual file-size limit is the administrator-configured per-file maximum (FR-005). Duplicate handling keeps its existing rules, with the fingerprint standardized by FR-010H.
- In the settings screen, values are labelled MiB and one MiB means 1,048,576 bytes, so saved values and the 100 MiB in-flight default are unchanged. Only the default per-file limit changes, from 4 MiB to 8 MiB, for installations that have not saved a value; this also changes the default of the existing optional parallel upload.
- This release connects only to Microsoft commercial cloud. National, sovereign, government, and other non-commercial Microsoft clouds require a future compatibility and compliance decision.
- Folder discovery includes descendant folders by default so a recruiter can submit a complete folder tree in one action.
- A submitted request represents the files identified during discovery up to the moment of confirmation; files added later, or not yet scanned, require another request or another discovery step. There is no per-file selection: every included file is imported.
- Completion notification is provided within the product; additional notification channels are outside this feature.
- Existing operational capacity controls govern how quickly accepted items are processed.
- "Raster PDF" means a PDF whose pages are rendered images of the original pages, without selectable or extractable text. Scoring relies on the visual content of the converted pages.
- The raster PDF choice applies to the whole request, not to individual files, and is off by default so existing behavior is unchanged unless a recruiter opts in.
- Source files that the product already accepts for scoring are eligible for conversion, except plain-text files, which are scored in their original form. Other files the product cannot render are reported as conversion failures.
- Conversion of Word (DOCX) and Markdown files relies on the source platform's own document-conversion capability (SharePoint and OneDrive both offer it). If it is unavailable in an environment, those types are excluded with a clear reason when the option is enabled.

## Dependencies

- An approved multi-tenant Microsoft 365 connection that can request delegated read access from work or school users, return them safely to the pending folder journey, and support background use for one confirmed request within the source tenant's policies.
- Verified publisher status for the connector before Production startup or feature activation; until verification, operation is restricted to controlled non-production Development or QA deployments whose product-user access is restricted by normal application authorization. This deployment gate has no source-tenant allow-list or source-tenant inspection.
- Source-tenant consent policies that either permit user consent or provide an administrator-consent path. No deployment-time host, root, site, drive, or folder grant is required.
- Protected storage capable of keeping pending and request-specific source authorization encrypted, isolated by its user/job/folder/request bindings, and automatically expiring or discarding it at the required lifecycle boundaries.
- Existing durable document import, candidate extraction, asynchronous scoring, status, retry, cancellation, and audit capabilities.
- Existing job scoring configuration and candidate-document validation rules.
- A document rendering capability able to produce image-based PDFs from the supported candidate document types (other than plain text), in the background.

## Out of Scope

- Writing, moving, renaming, or deleting content in SharePoint or OneDrive.
- Continuously watching a SharePoint or OneDrive folder for future files.
- Scheduling recurring folder imports.
- Changing scoring criteria, scoring calculations, or hiring decisions. Duplicate-handling rules are unchanged apart from standardizing the content fingerprint (FR-010H).
- Per-file selection within a discovered folder (every included file is imported).
- Retrying failures that occurred during scoring.
- Per-file conversion choices within a single request, or conversion of files outside this bulk scoring workflow.
- Writing converted documents back to SharePoint or OneDrive.
- Personal Microsoft account OneDrive, other cloud storage, and importing from personal devices through this workflow.
- Microsoft national, sovereign, government, and other non-commercial clouds.
- Any application-only or standing application-level access to SharePoint or OneDrive content, including tenant-wide access, deployment-time permitted hosts or roots, and pre-granted site, drive, or folder access.
- Reusing a Microsoft 365 source connection as a general account connection, browsing outside the pasted folder, or reusing authorization across users, jobs, folders, or requests.
- Personal Microsoft account authorization and fallback to application-only access when delegated authorization lapses.
- Sending completion notifications through email, SMS, or third-party messaging channels.

## Success Criteria *(mandatory)*

### Measurable Outcomes

Items marked *design goal* guide the design and are not formally measured.

- **SC-001** *(design goal)*: A recruiter can select an accessible folder, review discovered files, and submit a request on their first attempt without assistance.
- **SC-002**: Each discovery step of up to 1,000 eligible files returns within 60 seconds, and confirming a request of up to the configured maximum number of files is acknowledged and shows a trackable request within 60 seconds.
- **SC-003**: In 100% of acceptance tests where the browser is closed and the submitting machine is shut down after acceptance, processing continues and the latest status is available from another authorized device. The test is run in an environment that keeps the application running; development environments that suspend an idle application are excluded.
- **SC-004**: In mixed-outcome tests, 100% of eligible unaffected files continue to a terminal outcome when another file is unsupported, inaccessible, duplicated, or fails processing.
- **SC-005**: Aggregate status counts for included files match the recorded per-item outcomes for 100% of completed and cancelled requests, and the included count plus excluded counts by reason plus the unreadable count account for every entry scanned.
- **SC-006**: Repeated delivery, retry, or recovery of the same request item creates no duplicate application or scoring outcome for that item in 100% of resilience tests.
- **SC-007** *(design goal)*: Authorized recruiters can quickly identify every unsuccessful item and its available reason when opening request details.
- **SC-008**: Retrying failed or cancelled items creates a request containing only retryable pre-scoring items and unfinished items failed by a source-authorization lapse, and repeats none of the successful items in 100% of retry tests.
- **SC-009**: No user without access to the associated job can view or manage its bulk scoring requests in authorization testing.
- **SC-013**: In acceptance tests using work or school SharePoint and OneDrive folders from at least two Microsoft commercial-cloud organizational tenants, including a tenant different from the product user's tenant, 100% of accessible exact folders complete the same connect, verify, preview, and confirm journey without deployment-time source configuration.
- **SC-014**: Recruiters complete the same journey with the same steps for SharePoint and OneDrive and regardless of source tenant; no same-tenant/cross-tenant mode or source-tenant-specific product UI is shown, apart from consent or sign-in messages controlled by the source tenant.
- **SC-017**: In 100% of authorization tests, discovery and background import read only the confirmed folder and items the connected user can open, operate with no application-only or pre-granted folder access, and discard request-specific authorization within 15 minutes after the request reaches a terminal state or all source reads settle after cancellation.
- **SC-018**: In 100% of tests where request-specific authorization, consent, or source access is revoked while a request is running, every further source read stops; only items still needing source access fail with an access-related reason; securely imported, converting, or scoring items finish; completed items remain unchanged; the recruiter is notified; no fallback identity is used; and a retry is possible only after a new source connection succeeds.
- **SC-019**: In 100% of security tests, pending authorization expires after 30 minutes without recruiter activity and no later than 2 hours after it was obtained, cannot be used with a different product user, job, or folder, request-specific authorization cannot be used with a different request or folder, and no source authorization secret appears in client-visible data, administrator views, audit records, application logs, diagnostic logs, or error output.
- **SC-020**: In consent-path tests, a tenant that permits user consent lets the recruiter continue without administrator involvement, while a tenant that requires administrator consent returns no source content and shows an actionable approval path that can be resumed successfully after consent.
- **SC-010**: In 100% of requests submitted with raster PDF conversion enabled, every successfully scored item other than plain text has a retained original and a converted version with the same page count as its original, and every item that cannot be converted is reported failed with a reason.
- **SC-011**: In 100% of requests submitted without the raster PDF option, documents are scored in their original form and no converted documents are created.
- **SC-012**: A request using raster PDF conversion continues to completion after the submitting browser is closed and the submitting machine is shut down in 100% of acceptance tests.
- **SC-015**: In 100% of duplicate-detection tests, the same file is recognized as a duplicate regardless of which upload path (bulk scoring request, optional parallel upload, existing upload) or technology stack introduced the first copy, including documents uploaded before this change, and the "allow duplicates" option still permits intentional duplicates.
- **SC-016**: In 100% of tests with a folder larger than one discovery step, only files shown as included before confirmation are imported, discovery stops exactly at the configured file limit, and the recruiter is told clearly what is included and that everything else is excluded.
- **SC-021**: In tests at 1, 30,000, and 100,000 included files, authorized recruiters can page through every included draft item with no omissions or duplicates, while page navigation causes zero discovery continuations and changes neither the included total nor the discovery cursor.
- **SC-022**: In boundary tests, file-count values below 1 or above 100,000 and bulk total-byte values below 1 MiB or above 1 TiB are rejected; defaults are 30,000 files and 50 GiB; and changing either value after discovery starts does not change that draft's frozen limits.
- **SC-023**: In 100% of configuration-change tests, the version current at confirmation is retained, every item records or exposes the version actually used at scoring, current-version scoring is preserved, and a changed-version notice appears whenever a used or current version differs from the captured version.
- **SC-024**: In 100% of disclosure tests, folder and item names and verified source web URLs appear only in authorized request DTO/UI surfaces; permitted source-account labels are display names or masked emails; and forbidden source URLs, raw account identifiers, unmasked emails, and token material do not appear in logs, traces, metrics, audit payloads, errors, redirects, unauthorized responses, or administrator-generic surfaces.

- **SC-026**: In abuse tests, the 11th concurrent pending connection for one actor, the 11th start in a rolling minute for one actor, the 31st start in a rolling minute for one IP address, and the 61st callback in a rolling minute for one IP address receive a safe `429`; rejected requests redeem no code, acquire or refresh no token, make no Microsoft Graph call, and expose no restricted data.

- **SC-032**: In 100% of notification acceptance tests, each newly terminal request creates exactly one notification addressed only to its submitting recruiter; the notification contains the terminal outcome, accurate aggregate completed/failed/skipped/cancelled counts, and an authorized request-detail link; its payload contains zero item names; and one or more acknowledgment attempts leave exactly one retained acknowledgment and create no additional notification.
